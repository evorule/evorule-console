# evorule-console 边界与定位

> **Status**: v0.1.0
> **仓库**: gitee.com/evorule/evorule-console
> **本文档定位**: 只定"边界与定位",不定具体功能(功能规格见 [SPEC.md](./SPEC.md))

---

## 1. 一句话定位

> **evorule-console = evorule 的灵魂产品内核:不含 LLM、不含联网的完整规则引擎面板,展现 evorule"无智能、只有执行"的本质。它是大众版和高级版的共同基础。**

---

## 2. 它是什么

- **灵魂产品内核**:独立建仓,保持独立存在,不被某个衍生产品绑架
- **完整的规则引擎面板**:规则创建 / 执行 / 查看 / 审计 / 回放
- **展现 evorule 全部核心属性**(见 §4)
- **衍生产品的基础**:大众版(+联网+LLM)和高级版(保密行业定制)都基于它

---

## 3. 边界(不含什么)

| 不含             | 原因                                                                      |
| ---------------- | ------------------------------------------------------------------------- |
| **不含 LLM**     | LLM 是大众版/高级版的扩展;evorule-console 强调"无智能只有执行"            |
| **不含联网**     | evorule-console 本身不绑定网络栈;联网是衍生产品(大众版)实现层的事(见 §6)  |
| **不含 AI 编排** | AI 编排归 evo-agent 仓;evorule-console 不依赖 evo-agent(各仓独立发展原则) |

---

## 4. 展现 evorule 本质

| evorule 属性       | evorule-console 如何展现                |
| ------------------ | --------------------------------------- |
| JSON-in/out 自解释 | 规则用 JSON 表达,输入输出可读,自解释    |
| 确定性执行         | 同样输入永远同样输出,可视化展示执行过程 |
| 可回放             | 时间旅行能力(已嵌入 ttd 副本,见 §8)     |
| 可审计             | 完整审计链展示,blake3 哈希可验证        |
| 规则即数据         | 业务专家可改规则,无需编程               |
| TCB 纯净           | 消费 evorule 核心,0 依赖可信            |

**核心使命**:让项目方通过这个面板,**亲眼看到并相信** evorule 是一个"没有智能、只有执行"的确定性规则引擎。

---

## 5. 独立建仓的依据

1. 它是灵魂产品,必须保持独立存在,不被衍生产品绑架
2. 它是大众版和高级版的共同基础,独立建仓保证演化对称(两个衍生产品都基于同一内核)
3. 跟 evorule-server、evorule-sdk 独立建仓的演化路径一致(成熟后分仓)
4. 原在内部应用仓孵化,成熟后分仓独立(v0.1.0)

### 5.1 三独立仓模型

| 仓                  | 角色                                        | 版本号      | 依赖                                        |
| ------------------- | ------------------------------------------- | ----------- | ------------------------------------------- |
| **evorule-console** | 灵魂产品内核(无 LLM、无联网)                | 独立 semver | 0 依赖(消费 evorule 核心)                   |
| **大众版仓**        | evorule-console + 联网 + 云 LLM             | 独立 semver | `npm install @evorule/console@^0.1.0`(松绑) |
| **高级版仓**        | evorule-console + Tauri 嵌入 + 本地 GPU LLM | 独立 semver | `npm install @evorule/console@^0.1.0`(松绑) |

**核心原则**:各仓独立 semver,模块间**只依赖不绑定版本号**(`^x.x` 或 `latest`),各自优化演化,二次迁移零成本(本就独立)。

## 6. 关键技术决策:不含联网如何调 evorule 能力

evorule-console 不含联网,但要展现 evorule 的执行能力(evorule-reactor 是 Rust crate),前端(SvelteKit)如何集成?这是边界文档必须提出的核心矛盾。

采用抽象执行后端接口:evorule-console 定义"执行后端"抽象接口(如 `executeRule(rule, input) -> result` / `getSession(id) -> history`),具体实现可换。大众版用本地 HTTP(evorule-server loopback)实现,高级版用嵌入式(Tauri+Rust link evorule crate)实现。依据是 evorule-console 本身不绑定网络栈,是真正的基础——这样 evorule-console 本身不含联网,联网是大众版实现层的事。

> **开发期实现说明**:evorule-console 需要一个能跑的执行后端来开发调试。本仓用"本地 HTTP 实现"(调 evorule-server loopback)作为开发后端(`src/lib/backend/http-backend.ts`),但这不改变 evorule-console 的边界定义——它本身仍只依赖抽象接口,不绑定 HTTP。

**技术细节**(接口签名、数据契约、开发后端的具体实现)见 [SPEC.md](./SPEC.md)。

## 7. 跟 evorule 生态各仓的关系

| 仓                      | 关系                                                                                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **evorule**(核心)       | 提供机制层能力(reactor/governance/tcb),evorule-console 消费                                                                                    |
| **evorule-server**      | 大众版的执行后端实现(本地 HTTP);evorule-console 本身不直接依赖                                                                                 |
| **evo-agent**           | 平行独立产品,有自己的产品定位(编程 agent/助手 agent/特定领域 agent);可能复用 evorule-console,也可能不复用;**evorule-console 不依赖 evo-agent** |
| **evorule-sdk**         | evorule-console 可能用 SDK 调 evorule 能力(待功能规格定)                                                                                       |

**原则**:各仓以自己的目标定位独立发展,对其他仓的使用只是功能复用(避免重复造轮子),不构成服务依赖关系。

## 8. 跟 ttd 的关系

- ttd = time-travel-debugger,源码已整体复制进本仓 `src/lib/ttd/`(v1.0,性能优先原则)
- evorule-console 的"回放/调试"视图嵌入 ttd 源码副本,而非自己重写一套时间旅行能力
- 嵌入方式:整体直接复制(避免 iframe / 接口引用的跨边界调用开销)

**为什么整体复制而非重写或接口引用**:ttd 已 v1.0 稳定,5 视图 + What-If 完整;重写是重复造轮子,违反"功能复用"原则;接口引用引入跨边界调用开销,违反"性能优先"原则。

**同步策略**:ttd 在原仓独立维护,evorule-console 复制时记录版本号(见 `src/lib/ttd/VERSION.md`);ttd 升级时,在 evorule-console 的 CHANGELOG 记录同步。

### 8.1 嵌入方式取舍(通用原则,适用于所有集成)

嵌入与依赖有两种形式,取舍在性能 vs 便捷:

| 方式         | 描述                             | 性能                  | 便捷                  | 适用                   |
| ------------ | -------------------------------- | --------------------- | --------------------- | ---------------------- |
| **直接复制** | 把组件代码复制进 evorule-console | ✅ 优(零调用开销)     | ❌ 差(升级要手动同步) | 性能敏感路径           |
| **接口引用** | evorule-console 通过接口调用组件 | ❌ 差(跨边界调用开销) | ✅ 优(升级自动同步)   | 非性能敏感路径、开发期 |

**取舍原则:性能优先而非便捷优先**(这是 LLM 最容易犯的错——倾向便捷而牺牲性能)。

- 默认倾向"直接复制"(性能优),除非该集成点明确非性能敏感
- 具体每个集成点用哪种方式,在 SPEC.md 里按性能敏感度逐一判定
- 灵活处理:不一刀切,但警惕"为便捷牺牲性能"
